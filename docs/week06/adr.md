# ADR 006：PDF 預檢改用 Evaluator–optimizer，由 Host 規則評估後修訂一次

日期：2026-10-30。狀態：候選已實作並可切換，預設維持原版。第 02 組。

**問題。** PDF 預檢原本只呼叫模型一次：模型產生草稿，Host 依序核對行號、引用、配分與證據，遇到第一個錯誤就回傳 502、不給分。v0.8 開發期間以 gpt-4.1-mini 與非公開 PDF 的真實執行都卡在這裡：`ae1a441`（模型自寫引文）是 `UNGROUNDED_PDF_REPORT`，`a9010bf`（改為選行號後）是 `INVALID_SOURCE_REFERENCE`（跨頁、過長的行號範圍）。本週固定輸入上，原版用 gpt-4.1-mini 同樣回 502 `INVALID_SOURCE_REFERENCE`（文字證據的 `observation` 也填了說明）；用預設的 gpt-5.4 則通過。使用者只能整份重跑，模型也不知道哪一項錯、錯在哪條規則，同樣的錯可能再犯。

**決定。** 只改「模型草稿 → Host 核對」這段子流程，用 Evaluator–optimizer：

1. 模型產生草稿 A，Host 用 `evaluate_draft` 評估。它跑的是最終關卡同一套規則，但不在第一個錯誤就停：先列出全部行號問題與位置（如 `criteria[3].teacher_evidence`、`T1L10–T2L5`）；行號全部正確後，再列出全部配分與證據規則的違反。
2. A 通過就直接採用，呼叫次數與原版相同。A 未通過時，保存 A，把 A 與問題清單送回同一個模型，要求只修正被指出的位置，得到 B。
3. B 用同一套規則重評，另加一條修訂契約：不得把「僅從範例推測」改標成「明確要求」。通過才採用；仍未通過就停止，不給分、不寫入紀錄。上限 `MAX_DRAFTS=2`。

實作在 [`week6/workflow.py`](../../assignment_checker/week6/workflow.py)（112 行）；評估函式與既有關卡在 [`pdf_review.py`](../../assignment_checker/pdf_review.py)，主要是把核對規則拆成可逐項列出的形式（+163／−64 行）。沒有新增套件。`PDFPair.workflow` 選擇 `single`（原版，預設）或 `evaluator_optimizer`。

**為何是這一種。** 要擋的是可由程式精確判定的追溯性錯誤（行號跨頁、超出頁尾、欄位混用、配分數字不在引文中），Host 能指出確切位置，模型理論上能據此重選，正是「評估回饋後修訂」適用的情況。其他四種不符合本題：Chaining（先抽老師規格再比對學生）讓每次正常流程多一次呼叫，也修不到比對階段的行號錯誤；Routing 沒有需要分流的意圖；老師與學生 PDF 必須一起看才能比對，不是可獨立平行的工作；配分項目由老師規格固定，不需要模型動態派工。

**替代方案。**
- 換更大的模型：`13b2b1e` 已改用 gpt-5.4，與本案互補而非取代，兩者並存。
- 同一請求盲目重試：模型拿不到錯誤位置，等於再抽一次籤，也不算 workflow。
- 再加一個 LLM 當評估者：多一筆費用與延遲，而且它自己的判斷也無法核對；本題要擋的錯誤由程式判斷更準。
- Host 自動修正行號或清掉多填的欄位：等於由程式替模型挑證據，悄悄改變判斷，不採用。
- 修訂時只送文字、不重送 PDF 圖片：較省，但模型無法重看截圖，改用圖像證據時就是盲猜；暫不採用。

**資訊與支架決策。** 修訂呼叫拿到的資訊與第一次相同（系統提示、Host 擷取的原文行、兩份 PDF），另加草稿 A（以 assistant 回合送出）與問題清單。問題清單只含錯誤代碼、規則、位置、行號範圍、Host 的固定訊息與欄位層級的修正說明，不含 PDF 文字；不送 Session 記憶、身分、其他 run 或評估程式本身。評估者是 Host 程式而非模型，評估與最終關卡共用同一批規則函式；[test_week6_workflow.py](../../tests/test_week6_workflow.py) 的 19 種草稿中，「評估通過」與「最終關卡通過」逐一一致，採用前仍再跑一次 `validate_report`，所以修訂迴圈不會另立一套標準。

**停止條件。**
- 已達 2 份草稿仍未通過：`MAX_DRAFTS_UNRESOLVED`。
- 模型判斷檔案放反（`document_roles_match=false`），即使同一份草稿還有行號錯誤：`NOT_REVISABLE`。這是對檔案的判斷，不是引用錯誤；要求它重做只會給模型壓力去改成 true。
- 模型服務錯誤（逾時、額度、拒絕）：`PROVIDER_ERROR`，沿用原錯誤碼與 HTTP 狀態，不重試。
- 模型回覆無法解析：`DRAFT_UNUSABLE`。沒有設定金鑰：`CONFIGURATION_ERROR`，不計為呼叫。

每一種停止都把各份草稿的評估結果與停止原因放在錯誤回應的 `workflow` 欄位，介面直接顯示。回應中不含草稿內容、模型文字或尚未確認的分數。

**代價。** 只有 A 未通過時才多一次呼叫，但那一次要重送兩份 PDF 的頁面圖片。單次量測中，gpt-4.1-mini 候選失敗時 tokens 約為原版 2.3 倍、耗時約 1.9 到 3.1 倍；費用未計算。A 通過時（gpt-5.4 兩輪）呼叫次數相同。成功紀錄另存每份草稿 JSON（第一份通過 1 份、修訂後通過 2 份；含未確認分數，只存本機、不出現在回應）。

**風險。** Host 只能檢查可追溯性，不能檢查判斷是否正確。實測中 gpt-5.4 四次都寫出學生 PDF 裡不存在的終端機截圖並判為已完成，兩種流程都放行。修訂時模型也可能用「改成待確認」「改用圖像觀察」「改成沒有明確配分」來通過檢查。修訂提示禁止這些做法，「把範例推測改標成明確要求」由修訂契約直接拒絕；其餘情況只記錄在每份草稿的 `profile`（狀態分布、要求來源、證據種類、配分狀態），介面顯示「修訂改變」，讓人看得到但沒有自動阻擋。

**實測結果與修正。** 第一輪真實比較（`c0403a3`）中，gpt-4.1-mini 的草稿 A 有 8 項欄位混用，修訂稿與 A 逐字相同。我們判斷回饋只寫「欄位不可混用」太籠統，在 `327b7e2` 加入欄位層級的修正說明（`fix`）、標記「與上一份相同」，並在提示 v2 寫明原樣重送不會通過。第二輪的草稿 A 剛好沒有欄位混用，只有 1 項配分引用錯誤，`fix` 沒有實際送出；修訂稿仍與 A 完全相同。所以欄位層級回饋的效果尚未取得。第三輪在 `327b7e2` 重跑 gpt-5.4，結果與第一輪相同。三輪紀錄都保留，見 [前後比較](comparison.md)。

**回退。** 新請求改選原版，或 API 不帶 `workflow`（預設 `single`）。不需資料遷移；舊紀錄沒有 `workflow` 欄位也能讀取。

**預設維持原版。** 真實環境中修訂後通過的情況一次都沒有出現：gpt-5.4 不需要修訂，gpt-4.1-mini 兩次修訂都原樣重送；每列只有一次執行。候選失敗時 tokens 約為原版 2.3 倍（費用未計算），卻沒有換到結果，目前沒有理由設為預設。

**下一步。** 先改資訊形式再重測：把草稿 A 放進 user 訊息當作待修正資料，而不是 assistant 回合，檢查 mini 是否仍原樣重送；同時準備一份會產生欄位混用的固定草稿情境，真實驗證 `fix` 的效果。若仍無效，候選只對 gpt-5.4 開放。之後用多組合成 PDF、每組多次執行比較成功率，再決定是否切換預設。
