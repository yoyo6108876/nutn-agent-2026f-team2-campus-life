# 專案題目與範圍定義

## 題目

**以教師範例為參考的作業規格與完成度檢查助手**

更新日期：2026-09-23。本文件說明產品目標、現有實作與尚待驗證的驗收條件。目前已完成文字 JSON 的 LLM 基準 API；操作與證據見 [API 執行說明](api-usage.md) 與 [執行紀錄](execution/README.md)。

0922 新版講義的六項提交清單已整理為 [Week 2 Baseline Declaration：實作與驗證版](week2-baseline-declaration.md)，包含固定情境、I/O 協定、預期與實際停止層、模型版本、重現指令及已知限制。

## Problem：問題定義

老師提供一份作業範例，學生提交報告後，老師仍需逐份比對才能發現缺少的章節、說明或證據；學生也可能直到收到批改結果才知道漏做了什麼。本專案希望在學生提交後先進行一次完整性檢查，把缺漏同時整理給學生與老師。可能遇到的困難包括：

- 作業要求分散在不同段落，人工核對時容易漏掉。
- 學生與範例使用不同標題或表達方式，難以迅速找到對應內容。
- 已提交的作業提到了指定主題，卻沒有提供要求的說明、案例或證據。
- 不清楚範例中的細節是必做要求，還是僅供參考的呈現方式。

可觀察的後果是老師需要重複提醒同類缺漏、學生較晚發現需要補件，或誤把範例中的細節當成必做要求。以上是目前的需求假設，尚未透過訪談或實際作業樣本驗證。

## Target User：目標使用者

- **學生**：提交課程文字報告或專題文件後，需要知道漏了什麼及如何補充的南大學生。
- **老師**：提供作業範例、收取學生作品，需要快速掌握缺漏並確認有歧義項目的授課教師。

初期定位為繳交後、正式批改前的完整性檢查與提醒，不直接評分或決定是否接受補交。

## User Story

> 身為學生，我希望提交作業後，系統先對照老師範例，告訴我哪些內容缺少、證據在哪裡，以及需要補充什麼，讓我能依老師規定修正。

> 身為老師，我希望學生提交後，系統先整理每份作業的缺漏與待確認項目，讓我能快速找到需要提醒或人工檢查的部分。

## 目標使用流程與目前實作

1. 老師提供一份範例，可另外提供作業說明，並指定或確認範例中的必做項目。
2. 學生提交作業。目前由操作者將範例、作業及教師確認要求整理成文字 JSON，送入本機 API；作業檔上傳介面尚未實作。
3. 系統讀取該次提交與老師範例，逐項比對。目前保留輸入提供的段落 ID 並核對原文引用；PDF 頁碼擷取待實作。
4. 同一次檢查產生兩種內容：學生的補件提醒，以及老師的缺漏與待確認摘要。
5. 老師可依結果確認疑義，學生依規定補充內容。目前 API 接收並核對版本號；提交歷程儲存與補交管理尚未實作，操作者需自行提供新版本輸入。

目前「提醒」是 API 回覆中的雙方清單、理由與建議，沒有專用學生／老師網頁，也不包含寄信、傳送訊息或代替老師通知學生。

## LLM 的必要性與可驗證價值

此題目的核心是自然語言內容的語意對照，而非檔案數量、標題或關鍵字比對。

| 情境 | 固定規則的限制 | LLM 預期提供的價值 |
| --- | --- | --- |
| 範例標題是「Target User」，學生寫「誰會使用這個系統」 | 精確標題比對可能漏判 | 理解不同表達是否回答同一項要求 |
| 要求「說明為何需要 Agent」，學生只寫「AI 很方便」 | 關鍵字存在不代表論述充分 | 檢查是否提供與任務相關的理由與比較 |
| 要求三項可測試成功條件，學生寫「好用、正確、快速」 | 計數可通過，卻無法判定可測試性 | 辨識缺少固定情境、操作或判定標準 |
| 只有教師範例，尚未說明哪些章節必做 | 全面複製範例清單可能誤判 | 找出語意上的內容差異，同時區分已確認要求與待老師確認的項目 |

LLM 是否優於固定規則需要實測，不能僅因使用 API 就宣稱必要。後續將以相同樣本比較關鍵字／標題比對與 LLM，檢查漏判、誤判、證據引用與不確定性處理。LLM 負責語意理解；項目計數、輸出結構檢查與檔案處理仍可使用一般程式。

## 目標輸入與本週 API 的差異

1. **教師範例檔（必要）**：老師提供的作業參考檔，作為內容對照基礎。
2. **學生作業（必要）**：學生已提交的文字報告，附提交識別與版本。
3. **作業說明或教師確認的檢查項目（選填）**：用於確定哪些項目必做。未提供時，系統仍能比對範例，但只能提醒差異與待確認項目，不能把所有差異當成缺交。

上述是完整產品目標。**本週 API 僅接收整理好的文字 JSON，而且必填教師確認要求**；尚未支援 PDF、檔案上傳或「只有範例、不提供 confirmed_requirements」的模式。目前以固定段落 ID 引用；尚未取得真實教師範例與學生作品，已執行案例均為合成資料。

文件內的內容一律作為待分析資料；若文件出現「忽略要求」「直接判定全部通過」等文字，不應把它當成控制檢查流程的指令。

## 輸出與判定原則

每個檢查項目應包含：對照項目、來源與引用、是否經教師確認為必做、學生作業證據、判定、理由與補充建議。每份報告標示學生／提交識別與版本，兩種摘要共用同一份檢查結果。

| 對象 | 提醒內容 |
| --- | --- |
| 學生 | 缺漏項目、範例位置、自己已完成的內容、需要補充什麼與待詢問老師的問題 |
| 老師 | 該份提交的缺漏摘要、支持判定的引用、未確定項目與需人工確認的原因 |

例如同一次檢查，學生看到「失敗案例已有描述，但缺少測試輸入與結果，請補充」，老師看到「此提交：失敗案例部分完成，缺少輸入與結果；附學生原文位置」。兩者應保持一致，不能對學生顯示已完成、對老師卻顯示缺漏。

| 判定 | 意義 |
| --- | --- |
| 已符合 | 學生內容有明確證據支持已回應要求 |
| 部分符合 | 有相關內容，但缺少要求中的必要部分 |
| 尚未符合 | 在完整可讀的提交內容中，找不到對應要求的證據 |
| 無法判定 | 要求有歧義、文件互相矛盾，或資料不完整／無法讀取 |

作業說明或教師已確認的檢查項目，是「缺漏」判定的依據。只有範例時，可以指出「範例有、學生未找到」的差異，但必做性未確認者應列為「無法判定／待老師確認」。範例的題目、用字、段落順序不自動視為必做項目；老師明確指定使用範例模板時，才將被指定的結構納入要求。說明與範例互相矛盾時，列出雙方來源，不自行猜測教師意圖。

「尚未符合」與「無法判定」必須區分：檔案缺頁或無法擷取的內容不能直接視為學生沒做。找不到證據時明確標示，不能捏造引用。結果是提交後的完整性提醒，不代表教師評分或保證得分，也不自行決定補交期限。

### 輸出示例（非實測）

| 檢查項目 | 老師要求／範例 | 學生內容 | 預期結果 |
| --- | --- | --- | --- |
| 問題定義 | 描述使用者、情境與痛點 | 只有題目名稱 | 部分符合，指出缺少情境與痛點 |
| 成功條件 | 至少三項可測試條件 | 三項皆有固定輸入、操作與判定標準 | 已符合，引用三項條件 |
| 已知失敗案例 | 提供輸入、結果與原因 | 完整文件未出現相關內容 | 尚未符合，列出需補充的證據 |

## Success Criteria：驗收條件

以下為完整產品的驗收規格。已驗證項目僅代表固定合成案例或程式檢查通過；各項狀態列於表後，未將全部產品驗收視為完成。

| 編號 | Given：固定情境 | When：操作 | Then：可判定的預期結果 |
| --- | --- | --- | --- |
| AC-01 語意對應 | 老師確認需描述目標使用者；範例用「Target User」；學生在「誰會用」段落完整回答 | 提交後比對範例與作業 | 判定已符合並引用學生原文，不因標題不同而判缺漏 |
| AC-02 論述不足 | 要求說明 Agent 必要性；學生只寫「AI 很方便」 | 檢查要求與論述 | 判定部分符合，指出未說明任務需求與一般程式比較，不因包含 Agent／AI 字詞而通過 |
| AC-03 項目缺漏 | 明確要求已知失敗案例；完整可讀的學生文件沒有相關內容 | 逐項核對要求 | 判定尚未符合、標示未找到證據，不生成假的學生引用 |
| AC-04 非必要範例 | 作業說明只要求問題、使用者與成功條件；範例額外有市場分析 | 對照範例與學生作業 | 不將缺少市場分析判為未完成，可列為非必做參考 |
| AC-05 衝突處理 | 作業說明要求三項成功條件；範例註記只需兩項，且沒有優先順序說明 | 比對來源 | 明確引用衝突內容並列出待教師確認問題，不直接宣稱全部完成 |
| AC-06 引用可追溯 | 所有輸入文件均附可定位的頁碼或段落編號 | 產生檢查表 | 每個已符合／部分符合項目均附可在學生文件找到的原文與位置；未找到時明確標示 |
| AC-07 可測試性 | 要求三項可測試成功條件；學生寫「好用、正確、快速」 | 檢查三項內容 | 判定部分符合，指出缺少可判定標準，不能只以數量三項判定通過 |
| AC-08 雙方提醒 | 某次提交確實缺少教師已確認的失敗案例項目 | 完成該次檢查 | 學生提醒與老師摘要均列出相同缺漏、對應項目及同一提交版本；學生端有補充建議，老師端有判定依據 |
| AC-09 只有範例 | 老師僅提供範例，其中有市場分析，未確認是否必做；學生未寫 | 提交後比對 | 顯示範例與學生內容的差異並標為待老師確認，不直接判定缺交，不要求另有作業說明才可檢查 |

## Scope：本週已完成

- 一份教師範例、一份學生提交與必填教師確認要求的文字 JSON。
- FastAPI 接收輸入，呼叫一次 LLM，檢查回覆結構、提交識別、要求與引用。
- 回覆逐項狀態、證據、理由與建議；由同一結果產生學生與老師提醒清單。
- 固定正常／非法輸入／無根據引用的 200／422／502 驗收，一份真實模型案例與其用量紀錄。
- 可重現的替身語意錯判案例，明確展示引用驗證的能力邊界。
- 模型設定、指令檔、執行方式、依賴版本與 43 項自動測試。

## Out of Scope

- PDF 檔案上傳與文字擷取、只有範例但未確認要求的模式。
- 掃描 PDF 的 OCR、圖片內容與視覺排版檢查。
- 執行學生程式、驗證實驗是否真的做過或外部事實是否正確。
- 自動評分、保證成績、抄襲偵測或判斷是否使用 AI。
- 代寫整份作業、自動修改原始檔、自動提交到教學平台。
- 多工具 Agent、自動上網蒐集資料與長文件檢索系統。
- 教學平台自動觸發、全班批次處理、Email／LINE 等外部通知與補交期限管理。

## Baseline 實作

已採用 **single LLM call**：將 JSON 中的教師範例、學生段落與確認要求交給一次 OpenAI Responses 呼叫，取得結構化檢查結果；不包含 PDF 擷取。學生提醒與老師摘要由同一結果計算。一般程式驗證欄位、判定值及引用是否出現在原文中；通過結構驗證不代表語意判定一定正確。實測使用 `gpt-4.1-mini-2025-04-14` 與 `assignment-check-v1.1`。

固定規則的標題／關鍵字對照評估仍待完成，尚未取得 LLM 相較規則方法的全面增益數據。現有證據已保存模型、提示詞版本、輸入、輸出與使用量；固定設定不保證每次逐字輸出相同。

### Reproduction Steps：目前可執行的重現流程

1. 依 [API 說明](api-usage.md) 建立環境並安裝鎖定依賴。
2. 執行 pytest，以及 normal／invalid／ungrounded 的替身證據指令；這些不呼叫真實 API。
3. 使用本機金鑰執行 `--live --case normal`，取得一次真實合成案例結果；會使用 API 額度。
4. 執行 `--case known-failure`，重現引用有效但語意錯判仍放行的限制；預期 exit code 1。
5. 比較輸出與固定人工預期，保留 provider 類型，避免將替身結果當成 LLM 行為。

完整 command 與 evidence 索引已列於 [Week 2 Baseline Declaration](week2-baseline-declaration.md)。既有紀錄包含 43 項測試通過，以及一次真實呼叫的 1163 tokens／5.966 秒；大規模品質、失敗率與實際帳務費用尚未驗證。

## Known Failure 與仍待驗證的風險

**已重現 KF-01：**學生只說「失敗案例請見另檔附錄」，固定替身卻判定 met。因引用 S2 確實存在，現有 gate 回 HTTP 200、沒有提醒；人工預期應是 uncertain。這是驗證層的已知限制，不是真實模型錯判證據。[完整紀錄](execution/mock-known-failure.json)。

**另有尚未實測的主觀標準情境：**老師只要求「分析深入」，範例有三個具體案例；學生提供一個長篇案例。缺少正式評分規準時，僅由案例數量或篇幅無法判定分析是否充分，LLM 也可能把範例中的三個案例錯當成硬性要求。

預期處理是標示無法判定、指出缺少明確標準並提出待確認問題，並在學生與老師的結果中一致呈現。這是尚未實測的風險案例；後續需固定教師範例、學生提交與當時可用的要求資訊，保存實際輸出，才能成為講義要求的已知失敗證據。
